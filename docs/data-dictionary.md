### Sheet relationships (verified numerically)

```
Main data  (253 rows, Oct'25 + Nov'25)   <-- source of truth
   |
   |  filter to Oct'25 (125 rows) + roll 53 expense heads into 10 groups
   v
Branch Data (126 rows, Oct'25)  --- unpivot by expense head --->  Comparison (6,625 rows)
                                                                        ^
Group head (68 rows) --- expense head -> group head mapping ------------+
```

Proof of derivation:

| Check | Value |
|---|---|
| `Main data` Oct'25 Total Income | `39,624,883.74` |
| `Branch Data` Revenue (all rows) | `39,624,883.74` — identical |
| `Main data` Oct'25 Total Expense | `23,529,173.21` |
| `Branch Data` Total Expense | `23,529,173.21` — identical |
| `Comparison` Total Amount | `23,529,173.21` — identical |
| `Main data` Nov'25 Total Income | `41,951,316.83` |
| `Branch Data` Nov'25 rows | **0** — sheet is stale |

**Consequence for this application:** we ingest **`Main data`** (facts) and
**`Group head`** (mapping). `Branch Data` and `Comparison` are regenerated by the
MIS engine, so their staleness cannot desynchronise the reports.

> **The swapped `Quater`/`Month` headers are the single most important parser
> requirement in this dataset.** A parser that trusts header text alone will
> assign months to the quarter dimension and vice versa. Our importer resolves
> this from *value semantics* (`Oct'25` matches a month pattern; `Q3` matches a
> quarter pattern) and overrides the header. See [`parser.md`](./parser.md) §5.

## 5. Known defect in the existing Looker Studio report

The `% Revenue` column on PDF page 1 is computed against a **double-counted
revenue denominator**, an artefact of charting the long-form `Comparison` sheet
where each branch's revenue is repeated on every expense-head row.

Verified empirically:

| Reading | Denominator | Result |
|---|---|---|
| Looker's actual behaviour | `SUM(Total Revenue)` over the 119 rows in that group = `36,231,605.78` | `14,431,407 / 36,231,605.78` = **39.83 %** — reproduces the PDF |
| Grand total row | `SUM(Total Revenue)` over all 6,625 rows = `1,916,375,735.61` | `23,529,173.21 / 1,916,375,735.61` = **1.23 %** — reproduces the PDF |
| **Correct** figure | Oct'25 actual revenue = `39,624,883.74` | `14,431,407 / 39,624,883.74` = **36.42 %** |

The "1.23 %" grand total is the clearest symptom: expense is plainly ~59 % of
revenue for that month, not 1.23 %. The denominator scales with the *number of
expense heads charted*, so the percentage changes whenever a head is added.

**Our implementation reports the correct percentage** (`amount / revenue for the
same filter scope`). Because the client is accustomed to the old figures, the
MIS exposes a documented toggle, **"Looker-compatible % (legacy)"**, which
reproduces the old denominator for reconciliation during the changeover. It is
**off by default** and labelled as a known defect in the UI. See
[`mis-specification.md`](./mis-specification.md) §6.

## 6. Fiscal calendar derived from the data

* Month values present: `Oct'25`, `Nov'25` — parsed as `2025-10`, `2025-11`.
* Quarter column value: `Q3` for both — consistent with the Indian fiscal
  calendar (Apr–Jun Q1, Jul–Sep Q2, **Oct–Dec Q3**, Jan–Mar Q4).
* Financial year: **FY 2025-26** for both months.

The application derives quarter and financial year from the month and
**validates** them against the source quarter column, raising a
`QUARTER_MISMATCH` warning on disagreement rather than silently trusting either.
See [`mis-specification.md`](./mis-specification.md) §2.

## 7. Fields deliberately **not** modelled

Per the build specification's "do not invent values" rule, the following have no
support in the source data and are absent from the schema:

| Field | Why absent |
|---|---|
| Voucher / transaction detail | `Main data` is pre-aggregated to branch-month-account. No voucher numbers, dates, parties or narrations exist. Drill-down stops at the expense head and links to the originating import row. |
| Ledger (individual Tally ledger) | Only ledger *groups* (expense heads) are present. The Tally adapter will supply true ledgers when connected. |
| Cost centre | Not present in the workbook. `Centre` here is a geographic region (`WESTERN`/`CENTRAL`), not a Tally cost centre. |
| Debit / credit split | Only net signed amounts are present. |
| Daily dates | Grain is monthly. |

These remain in the Prisma schema as **nullable** columns so a future Tally sync
can populate them without a migration that rewrites existing data.
